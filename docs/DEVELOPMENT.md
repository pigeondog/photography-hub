# 开发流程与检查指南

[项目约束](../AGENTS.md)规定开发边界，[需求基线](../PROJECT_SPEC.md)描述业务和技术默认值。本指南规定如何执行，不另行复制一份需求规格。

## 当前状态

当前仅有需求文档和开发流程工具，没有业务工程、Git 仓库、CI 或分支保护。本次不引入第三方 skills 和依赖。

可运行的检查是文档结构、本地文件链接及变更记录格式检查。前后端、Worker 和本地助手的代码检查尚未配置，文档检查通过不代表它们通过。

## 一次修改的流程

1. **理解变更**：阅读相关规格、实现和历史决策，说明新旧行为、影响模块及规格中的验收编号。未确认的高影响规则先明确。
2. **检查设计**：检查数据所有权、依赖方向、接口消费者及现有职责。必要时先做局部重构；不顺带换技术栈或全面重写。
3. **实现与清理**：围绕一个可验证行为组织修改，结构调整与行为变更分别可审查；清理失效路径，兼容代码写明移除条件。
4. **验证与审查**：执行适用检查，覆盖成功、冲突、重试和失败等受影响边界；审查重复业务规则、越界依赖及旧逻辑残留。
5. **同步与交付**：更新规格、变更记录和相关决策，说明实际执行的命令、结果、未执行原因及剩余风险。

明确需求自主推进。只在关键业务歧义、模块边界或技术栈改变、破坏性数据操作时请求确认；既有授权不重复询问。

## 何时记录变更

以下变化需要在 `docs/changes/` 保存简短 Markdown 记录，文件名采用 `YYYY-MM-DD-简短主题.md`：

- 新增、替换或删除业务行为。
- 改变公开接口、持久化数据结构、文件操作方式或模块边界。

文案、轻微样式调整和不改变既定行为及上述契约的小修复可以免写记录，交付时仍须说明验证。数据相关修复不能借“小修复”免去记录。

记录在开始实现前写明目标、设计和验证计划；完成后补充实际结果。需求变化同步修改基线，不能只留在聊天或变更记录中。跨阶段工作引用已有记录，不为了每个小步骤重复建文档。

### 变更记录模板

复制以下模板并填写。六个二级标题保持原样，其他内容可以按需补充。占位项在提交检查前必须替换；验证尚未执行时如实写明计划和原因。

```markdown
# 变更：简短主题

## 变更目的与行为差异

待填写

## 影响范围与设计

待填写

## 验收场景

待填写

## 验证计划与结果

待填写

## 清理与兼容

待填写

## 风险与恢复

待填写
```

填写说明：

- **变更目的与行为差异**：为什么改，原来如何，改后如何；关联需求基线章节。
- **影响范围与设计**：涉及的模块、数据和接口消费者；职责是否调整，是否需要决策记录。
- **验收场景**：引用需求基线已定义的 `AC-xx`，说明本次如何验证。新增行为先补齐基线验收场景；无对应业务验收时写“不适用：具体原因”，并说明本次自身的验收条件。
- **验证计划与结果**：列出适用检查、边界场景、实际命令及结果。未执行应写原因，不把计划当结果。
- **清理与兼容**：列出旧逻辑清理；无兼容需求时明确说明。保留兼容时说明原因和移除条件。
- **风险与恢复**：说明数据、文件、契约风险及可行恢复方式；涉及数据库时区分应用回退与数据恢复。文档变更可以说明如何撤回。

脚本只检查格式、非空和引用存在性，不能判断设计合理性、理由是否充分或测试是否真的执行；这些内容必须由开发者和审查者验证。

## 架构决策记录

重要技术选型、模块边界和跨模块契约的选择，记录在 `docs/decisions/`，仅在有实际决策时创建文件。普通实现细节无需 ADR。

每份记录包含：编号与主题、日期、状态、背景、备选方案、选择及取舍、相关变更记录。状态采用“拟议／已接受／已拒绝／已替代”。用户已经明确确认的决定可直接记录为已接受，无需再次审批。

已接受的决策被改变时新增记录，旧记录只补充已替代状态和新决策引用，不抹除原来的理由。尚未发生的决策不得提前标记为已接受。

## 现在如何运行检查

在项目根目录执行，使用 Python 3.9 或更新版本，无需安装依赖：

```sh
python3 scripts/check_project.py
python3 scripts/check_project.py --change docs/changes/2026-10-30-development-workflow.md
python3 -B -m unittest discover -s tests -v
```

- 默认检查根目录的项目约束、需求基线、开发指南是否存在，以及它们和 `docs/` 下全部 Markdown 的本地文件链接。
- `--change` 在上述检查之外，检查指定记录的六个必需栏目、非空内容、未替换占位行及验收编号。路径相对项目根目录，也支持指向本项目记录的绝对路径；记录必须位于 `docs/changes/` 下。
- 本地链接支持行内链接、图片及引用式链接的定义，允许 URL 编码和尖括号路径；相对文档解析，`/` 开头的路径相对项目根目录。文件必须位于项目内并指向真实文件。
- 跳过围栏代码块、行内代码、HTML 注释、外部 URL 和纯锚点。仅校验文件存在性，不检查标题锚点、远程网站可达性、HTML 链接或完整 CommonMark 语法。
- 失败返回退出码 `1`，输出文件和行号；命令参数错误返回 `2`。成功只说明执行过的文档检查通过。
- 提交涉及记录的修改前，对每份新增或修改的记录分别执行 `--change`。模板写在本指南的代码块中，不作为正式记录检查。

## 工程建立时必须接入的检查

以下目前均为**未配置**。首次建立对应工程时，在同一变更中配置、锁定依赖和运行时版本，补充准确命令、执行位置和通过结果；不能以本指南或文档检查替代真实检查。

| 子系统 | 必须接入的检查 | 验证重点 |
|---|---|---|
| 前端 | 格式、Lint、TypeScript、生产构建、模块依赖 | 展示与状态职责、跨模块公开入口、循环依赖 |
| 后端与 Worker | 格式、Lint、类型、模块依赖、相关 pytest | 共用业务规则、数据所有权、任务幂等及失败恢复 |
| 本地助手 | 格式、Lint、类型、相关 pytest | 契约通信、身份与索引、冲突、中断和安全恢复 |
| 前后端接口 | OpenAPI 导出、TypeScript 类型生成一致性、消费者验证 | 禁止手改生成文件，破坏性变更覆盖受影响消费者 |
| 关键流程 | 必要的集成测试和 Playwright | 根据需求基线验收场景选择，验证用户可观察行为 |

前端边界检查应阻止访问其他业务模块内部路径；Python 边界检查应阻止业务模块越界依赖、基础层反向依赖和循环依赖。测试还须验证跨模块行为，静态 import 检查不等于数据所有权已验证。

文件测试使用临时目录和独立 JPG 样本，不操作真实照片库。模型及外部服务测试默认使用替身；真实调用按已有授权和配置执行，不让日常检查依赖个人 Key 或产生隐式费用。

涉及库存、照片关联、任务和文件操作时优先覆盖并发、重复提交、部分失败和恢复；低影响界面调整采用适当的直接验证，不为覆盖率编写与实现一一对应的测试。

工程基础阶段只有在对应检查实际配置并通过、相关行为可验收时才可标记完成。Git 和托管平台建立后，再将相同命令接入 CI 和合并门禁；本次不配置。

## 交付与审查清单

- 行为是否与当前需求一致，相关未定问题是否已经解决或明确留待后续？
- 规则是否只有一个权威实现，跨模块访问是否通过公开接口？
- 新设计是否解决当前问题，旧逻辑是否清理，兼容是否有退出条件？
- 接口消费者、数据迁移、失败恢复和本地文件边界是否验证？
- 记录中的命令是否实际运行，是否区分通过、失败、未执行和未配置？
- 规格、变更记录和架构决策是否同步，是否说明剩余问题？
